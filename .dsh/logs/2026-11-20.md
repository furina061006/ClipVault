# 2026-11-20 · ClipVault 崩溃排查与重构

> 记录人：DeepSeek Harness 会话
> 时间范围：约 04:51 – 05:50（Asia/Shanghai）
> 环境：Ubuntu 22.04.5 / X11 / Python 3.10.12 / Qt 5.15.14 / PyQt 5.15.11

---

## 1. 起因

用户反馈 pip 包 `clipvault`（Windows 风格剪贴板管理器）"偶尔会被 kill"。
最初的现象只是窗口/托盘图标隔一阵子消失，systemd 3 秒后又把它拉起来。

---

## 2. 先确认：不是被 kill，是自己 abort

查 `journalctl --user -u clipvault`：

```
clipvault[24846]: double free or corruption (fasttop)
clipvault.service: Main process exited, code=dumped, status=6/ABRT
clipvault.service: Failed with result 'core-dump'.
```

几次崩溃时间：04:29:47、04:45:10、04:49:49，间隔 2–15 分钟不等。

`/var/log/apport.log` 里从 11-19 到当天共有 20 条 clipvault 记录，全是 `signal 6`。
`dmesg` 里没有任何 OOM 记录。

结论：**glibc 检测到堆内存被破坏（double free）后主动 SIGABRT**，
属于 Qt / Pillow 这一层 C/C++ 扩展的内存 bug，不是系统杀进程，也不是内存不足。
service 配了 `Restart=on-failure` + `RestartSec=3`，所以表现成"偶尔闪断又自己回来"。

---

## 3. 代码层面看到的可疑点

原始代码里 `ClipboardWatcher` 是个 `QThread`，在子线程里直接调用：

- `QApplication.instance().clipboard()`
- `cb.mimeData()` / `cb.image()`
- `img.bits()` + `img.byteCount()` 交给 Pillow，且一律按 RGBA 解析（不管 QImage 实际格式）
- 整个轮询循环包在 `except Exception: pass` 里，出错完全无记录

`QClipboard` / `QImage` 是 GUI 相关对象，Qt 要求只在 GUI 线程使用；
在 X11 下跨线程访问属于未定义行为，是这次堆损坏的头号嫌疑。

---

## 4. 走过的一些弯路（留给以后的自己）

1. **gdb 复现**：用 `gdb -batch -ex run` 跑，结果自定义的 SIGUSR1（切换窗口）被 gdb 默认拦截，
   进程被 gdb 停在信号处直接退出，误以为"崩了"。
   → 以后要么 `handle SIGUSR1 nostop noprint pass`，要么别用 SIGUSR1 做实验。
2. **指望 `QClipboard.changed` 信号**：实测 4 次跨进程接管剪贴板只收到 1 次信号，不可靠。
3. **想用 `TIMESTAMP` target 做变更令牌**：Qt 自己持有剪贴板时返回空，不可靠。
4. **怀疑托盘 QMenu 生命周期**：`setContextMenu()` 后菜单没有 Python 引用，
   一度以为是悬空指针。实测 PyQt5 会保活到进程结束，排除。
5. **压力测试**：文本/图片/开关窗口/XTEST 模拟点击，跑了 30 多分钟都没复现——
   说明是概率性问题，只能先上"行车记录仪"。

## 5. 实测数据（决定方案的关键）

| 操作 | 耗时 |
|---|---|
| `cb.mimeData()` | ≈ 27 µs |
| `cb.text()` | ≈ 0.36 ms |
| `cb.image()`（2560×1440，跨进程） | **≈ 180 ms**，且每次都重新取 |

所以图片绝不能放进 500ms 轮询里，必须做变更检测/降频。

## 6. 最终改动

### 6.1 先装"行车记录仪"

- 新增 `clipvault/diagnostics.py`
  - Qt 加载**之前**启用 `faulthandler`，SIGABRT/SIGSEGV 时把**所有线程**的 Python 栈写盘
  - 普通日志 `clipvault.log`：2 MB × 4 轮转
  - 崩溃栈单独写 `crash.log`：5 MB × 2 轮转
    （分开的原因：faulthandler 持的是裸 fd，跟不上 RotatingFileHandler 的改名）
  - 捕获 Qt 自身警告、主线程/子线程未捕获异常、SIGTERM/SIGINT/SIGHUP
  - 自建 self-pipe + `QSocketNotifier`，让信号在 Qt 事件循环空闲时也能立即处理
    （原来空闲时 SIGUSR1 / SIGTERM 根本不会被处理，停止服务也不留痕）
  - `kill -USR2 <pid>` 可随时手动 dump 全部线程栈

### 6.2 剪贴板轮询搬回 GUI 线程

- `ClipboardWatcher`：`QThread` → `QObject` + `QTimer`，挂在主窗口下
- 文本：每 500ms 轮询（便宜）
- 图片：仅当"格式列表变化"或"距上次读取 ≥ 5 秒"才真正 `cb.image()`；
  读到后用 16×16 缩略图指纹比对，指纹没变就跳过 PNG 编码
- 图片统一 `convertToFormat(RGBA8888)` + `sizeInBytes()`，不再硬套 RGBA
- 退出时干净停表（`app.aboutToQuit` → `window.shutdown()`）
- 历史保存、热键回调的异常不再静默，全部落日志

### 6.3 其它顺手修的

- `--version` 提前返回，不再创建日志会话
- 托盘菜单显式保留引用（防御性，非本次主因）
- 日志中记录粘贴、开关窗口、剪贴板捕获事件，便于事后还原时间线

## 8. 打包问题：`app/` 还是 `clipvault/`

原包在 site-packages 里落地成顶层 `app/`，因为上游 `pyproject.toml` 写的是：

```toml
[project.scripts]
clipvault = "app.main:main"
[tool.setuptools.packages.find]
include = ["app*"]
```

发行名 `clipvault` 与导入名 `app` 不一致。后果：容易与其它叫 `app` 的包冲突，
`pip uninstall` 按 RECORD 删文件时也可能误伤。

处理：

1. 把安装目录里的 `app/` 还原成源码工程，重命名为 `clipvault/`
2. 全量替换 `from app...` → `from clipvault...`，同步 pyproject
3. 构建 wheel 验证：顶层包 = `clipvault`，entry point = `clipvault.main:main`
4. 卸载旧的、装新的；`import app` 现在会 ModuleNotFoundError

### 中途踩的坑：pip 22.0.2 打出 `UNKNOWN-0.0.0`

不管 pyproject 怎么写，老 pip 构建出来的 wheel 都是 `UNKNOWN-0.0.0`
（Metadata-Version 2.1，setuptools 根本没读 `[project]`）。
直接调用 `setuptools.build_meta` 却正常。换 `pip 26.3` 后立刻正常。

→ 已执行 `python3 -m pip install --user -U pip`，当前 pip 26.3。

## 12. 经验教训

1. **不要在 site-packages 里直接改代码**——那次改动只能靠手动备份回滚，
   正确做法是先还原成源码工程，再改、再构建、再安装。
2. **Qt 的 GUI 对象（QClipboard/QImage/QPixmap）不要跨线程用**，
   即使"看起来能跑"，也是未定义行为。
3. **日志必须轮转**，而且 faulthandler 的输出要单独放一个文件。
4. **信号处理在 Qt 事件循环里不会自动执行**，要配 `set_wakeup_fd` + `QSocketNotifier`。
5. **压力测试不复现 ≠ 没问题**；这类堆损坏本身就是概率性的，
   先把证据留下来比盲目重构更重要。
6. 排查时先分清 **SIGKILL / SIGTERM / SIGABRT / 段错误**，
   这次一开始被"被 kill"的说法带偏了一会儿。
